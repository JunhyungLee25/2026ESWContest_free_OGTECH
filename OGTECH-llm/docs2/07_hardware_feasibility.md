## 0. 한 줄 답

> **연산은 넉넉합니다. 메모리는 빠듯합니다. 전력과 열이 진짜 문제입니다.**
>

> **하드웨어가 동결되어 있으므로 듀티 사이클링으로 우회합니다.** ([06](06_power_budget_battery.md))

## 2. 연산 — ✅ 문제없음

Xavier NX는 **21 TOPS급 엣지 AI 보드**입니다. 우리가 시키는 일은 그 능력의 극히 일부입니다.

| 부하 | 실측/추정 | 여유 |
|---|---|---|
| LLM prefill | **413 tok/s** `[실측]` | 프롬프트 60~350 tok → 0.15~0.85 s |
| LLM 생성 | **27 tok/s** `[실측]` | 96 tok → 3.6 s (스트리밍으로 체감 완화) |
| 벡터 타일 렌더링 | WebGL, 1024×600 | `[미검증]` 프레임률 측정 필요 |
| A* 길찾기 (노드 1만 개) | < 50 ms | `[추정]` |
| 일출몰 (Meeus) | 수십 μs | `[추정]` |
| Zambretti | 산술 몇 줄 | 무시 가능 |

**"연산이 부족해서 못 한다"는 상황은 없습니다.**

## 3. 메모리 — ⚠️ 빠듯함

**OS 인식 RAM 6.8 GB** 기준.

| 구성 | 기존 (의료) | 신규 (오지) `[추정]` |
|---|---:|---:|
| OS + 데스크톱 | 1.0 | 1.0 |
| Chromium kiosk | 0.8 | **1.2** (WebGL 벡터 지도) |
| Python 백엔드 | 0.2 | **0.3** (지도 타일 서빙·센서) |
| LLM 상주 | 1.4 | 1.4 |
| STT 온디맨드 | 0.5 | 0.5 |
| **TTS 온디맨드** | — | **0.5 ~ 1.5** |
| **동시 피크** | **4.3 / 6.8** | **4.9 ~ 5.9 / 6.8** |
| **여유** | 2.5 GB | **0.9 ~ 1.9 GB** ⚠️ |

### 지켜야 할 규칙 3개

1. **STT와 TTS를 동시에 올리지 않습니다.** 둘 다 온디맨드 로드/언로드.
   → `harness/tts.py`에 스케줄러가 필요합니다 ([05 §8](05_llm_harness_redesign.md)).
2. **지도 타일 캐시에 상한을 겁니다.** Chromium이 타일을 무제한 캐싱하면 그대로 OOM입니다.
3. **자체 게이트 유지: `MemAvailable ≥ 1 GB`.** 위반 시 TTS를 espeak-ng로 강등하고 계속 동작.

> **TTS가 1.5 GB짜리면 여유가 0.9 GB로 내려가 자체 게이트에 걸립니다.**
> 이게 [05 §6.3](05_llm_harness_redesign.md) W1 스파이크가 급한 이유입니다.

## 4. 열 — ⚠️ 새로 생긴 문제

**기존 작품은 구급함이었습니다. 케이스가 크고, 환기가 되고, 실내에 놓였습니다.**
신규는 **밀폐 방수 케이스 안, 배낭에 밀착, 등에 붙어서, 직사광선 아래**입니다.

| 조건 | 영향 |
|---|---|
| IP65 밀폐 | **공기 대류 없음.** 방열은 케이스 전도에만 의존 |
| 배낭 밀착 | 한 면이 사용자 등에 막힘 |
| 직사광선 | 검은 케이스 표면 온도 60°C 이상 가능 `[추정]` |
| Xavier NX 발열 | 13~19 W 부하 시 상당량 |

**Xavier NX는 85°C 부근에서 스로틀링합니다.**
밀폐 케이스 + 여름 직사광선 + 지속 부하면 **성능 저하 또는 셧다운**이 현실적입니다.

### 완화 방안 (우선순위 순)

| # | 방안 | 효과 | 비용 |
|---|---|---|---|
| 1 | **듀티 사이클링 자체가 최고의 열 대책** | 평균 부하가 0.4 W면 열이 안 남 | 0 |
| 2 | 케이스 금속면에 히트파이프/서멀패드 직결 | 케이스 전체를 히트싱크로 | 낮음 |
| 3 | 파워 모드 10W 고정 | 피크 억제 | 0 |
| 4 | 온도 기반 자동 강등 (`tegrastats` 감시) | 안전 | 낮음 |
| 5 | 방수 벤트(Gore-Tex 통기막) | 제한적 대류 | 중간 |

**측정 필수 (W2)**: 밀폐 케이스에 넣고 30분 지속 부하 후 `tegrastats` 온도·클럭 로그.
실측하지 않은 상태에서는 보고서에 확정값으로 쓰지 않습니다.

## 5. Xavier NX가 이 작품에 맞는 보드인가 — 정직한 평가

### 안 맞습니다

| 지표 | Xavier NX | 이 작품이 원하는 것 |
|---|---|---|
| 설계 전력대 | 10~15 W (모듈) | **1 W 이하 평균** |
| 유휴 소비 | 7.3 W | 0.3 W |
| 부팅 시간 | 15초 이상 `[미검증]` | 즉시 |
| 전제 전원 | 상시 (차량·산업) | 배터리 |
| 방열 전제 | 히트싱크 + 대류 | 밀폐 |

**더 맞는 대안** (참고용, 채택 제안 아님): ESP32-S3 + 저전력 MCU 조합, Raspberry Pi Zero 2W,
또는 Jetson Orin Nano (동일 성능에서 더 나은 전력 효율).

### 그런데도 Xavier NX를 유지하는 이유

| 사유 | 설명 |
|---|---|
| **하드웨어 동결** | 대회 4주 전. 보드 교체는 소프트웨어 스택 전체 재검증을 의미 |
| **실측 자산** | Qwen2.5 1.5B의 4.3/6.8 GB, 413/27 tok/s가 **이 보드에서 측정된 값** |
| **STM32 이중 계층이 약점을 상쇄** | 상시 계층을 MCU가 맡으면 Xavier의 유휴 소비는 무의미해짐 |

> **심사위원 대응**: "왜 이렇게 전력 많이 먹는 보드를 썼나요?"에 대한 답은
> **"동결된 제약이라 우회 설계를 했다"** 입니다. 변명하지 말고 **STM32 이중 계층 다이어그램을 보여 주세요.**
> 제약 조건 하에서의 설계 결정은 감점이 아니라 **기술성 항목의 가점 요인**입니다.
