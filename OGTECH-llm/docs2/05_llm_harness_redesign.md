# 05. LLM 하네스 재설계 — 오지 생존 도메인

요구 3.4에 대한 답입니다.
질문 원문: *"마이크로 LLM에게 질문하면 LLM이 연산해서 귀에 연결된 스피커로 답을 주는 구조.
QWEN2.5 1.5B로 그대로 사용할 예정인데 충분할지. 하네스 어떻게 할지"*

## 1. 결론부터

| 질문 | 답 | 신뢰도 |
|---|---|---|
| **Qwen2.5 1.5B로 충분한가** | **역할을 지키면 충분. 지식 원천으로 쓰면 안 됨.** | 높음 |

| 최대 미해결 리스크 | **한국어 오프라인 TTS 품질과 메모리.** 후보는 있음 (§6) | 중간 |

## 2. Qwen2.5 1.5B — "충분한가"를 역할별로 쪼개기

"충분한가"는 하나의 질문이 아닙니다. 3개입니다.

| 역할 | 요구 능력 | 1.5B로 되나 | 근거 |
|---|---|---|---|
| **1. 발화 → 라벨 14개 중 1개** | 짧은 텍스트 분류 | ✅ **충분** | 문법 제약(GBNF)으로 출력이 라벨 집합에 강제 갇힘. 남는 건 정확도뿐이고 9→14 라벨은 여전히 소형 모델 범위 |
| **2. 발화 → 구조화 필드 추출** | 개체 추출 | ✅ **충분** | JSON Schema 제약. 예: "베이스캠프까지 얼마나 남았어" → `{target: "basecamp", ask: "distance"}` |
| **3. 고정 카드 → 2~4줄 상황 맞춤 문장** | 짧은 생성, 재작성 | ✅ **충분** | 입력에 사실이 다 들어 있고 모델은 재구성만 함 |
| **4. 생존 지식 질의응답** | **사실 회상** | ❌ **절대 불가** | 아래 |

**4번이 위험한 이유** `[출처]`

- Qwen2.5는 MMLU 같은 표준 벤치마크 점수를 위해 **일반 상식·문화 지식 토큰을 상당 부분 희생**했다는 관측이 있습니다.
- MMLU는 **객관식**입니다. 흐릿한 기억으로도 가장 가까운 보기를 고르면 맞습니다.
  **0-shot 실제 질문**에서는 같은 흐릿함이 그대로 환각으로 나옵니다.
- 즉 **"MMLU 점수가 괜찮으니 생존 지식도 알겠지"는 성립하지 않습니다.**

> **그래서 계약이 이렇습니다:**
> 사용자가 "저체온증 어떻게 해요"라고 물으면 →
> 모델은 **`warmth` 라벨만 뱉고**, 화면·음성에 나가는 문장은 **검수된 고정 카드**입니다.
> 모델이 저체온증 처치법을 "아는지"는 우리 설계에서 **아무 의미가 없습니다.**

## 3. 새 파이프라인과 지연 예산

### 3.1 기존 vs 신규

```
[기존]  터치 → (LLM 분류) → 고정 카드 → 화면
[신규]  마이크 → STT → 분류 → 고정 카드 → (LLM 다듬기) → TTS → 이어 스피커
                                              ↑ 선택적
```

**단계가 2개에서 5개로 늘었습니다.** 각 단계가 지연을 더합니다.

### 3.2 Xavier NX 실측 기반 지연 계산

기준 수치 (기존 문서에서 승계):

| 항목 | 값 | 출처 |
|---|---|---|
| prefill | **413 tok/s** | `[실측]` |
| generation | **27 tok/s** | `[실측]` |
| LLM 상주 메모리 | 1.4 GB (4.3/6.8 총점유) | `[실측]` |

**경로 A — LLM 다듬기 포함 (긴 경로)**

| 단계 | 계산 | 시간 |
|---|---|---|
| STT (5초 발화, whisper.cpp base, CUDA) | RTF 0.2 가정 | **1.0 s** `[추정]` |
| 키워드 1차 분류 | 정규식 | **~0 s** |
| (키워드 실패 시) LLM 분류 | 200 tok prefill ÷ 413 + 라벨 1~3 tok | **0.6 s** |
| 카드 조회 (SQLite) | 인덱스 조회 | **~0 s** |
| LLM 다듬기 prefill | 350 tok ÷ 413 | **0.85 s** |
| LLM 다듬기 생성 (96 tok 전량) | 96 ÷ 27 | **3.55 s** |
| TTS 첫 청크 | RTF 0.3 가정 | **0.3 s** `[추정]` |
| **총 (전량 대기 시)** | | **≈ 6.3 s** ❌ |
| **총 (첫 문장 25 tok에서 TTS 시작)** | 1.0 + 0.85 + 0.93 + 0.3 | **≈ 3.1 s** ⚠️ |

**경로 B — LLM 다듬기 생략 (짧은 경로)**

| 단계 | 시간 |
|---|---|
| STT | 1.0 s |
| 키워드 분류 | ~0 s |
| 카드 조회 | ~0 s |
| **카드 문장을 TTS로 바로 재생** | 0.3 s |
| **총** | **≈ 1.3 s** ✅ |

### 3.3 이 계산에서 나오는 설계 결정 3개

**결정 1 — P0 응답은 LLM을 아예 거치지 않습니다.**

```
lost / daylight / warmth / sleep_safety / injury  →  경로 B (고정 카드 직행 TTS)
route / weather / water / gear / food             →  경로 A (LLM 다듬기 허용)
refuse                                            →  경로 B (고정 거부 카드)
```

**더 빠르고 동시에 더 안전합니다.** 생명이 걸린 경로에서 모델을 빼는 게 정답입니다.
이건 구 도메인의 계약 1번("생명위험 분기는 LLM보다 앞에서 코드가 처리")과 같은 원리입니다.

**결정 2 — 문장 단위 스트리밍 TTS는 필수입니다.**
96토큰 전량 생성을 기다리면 6.3초입니다. 첫 문장에서 바로 재생을 시작해야 3초 안에 들어옵니다.

**결정 3 — STT·LLM·TTS는 절대 동시 실행하지 않습니다.**
기존 규칙 그대로. Xavier의 통합 메모리를 GPU 렌더링(지도) + LLM + STT가 나눠 씁니다.

## 4. 프롬프트 조립 — 순서 규칙은 그대로, 내용만 교체

**불변 → 준가변 → 가변** 순서를 유지합니다. 이걸 어기면 매 요청 KV 캐시가 통째로 날아갑니다.

```
[SYSTEM + 출력 규칙]      ← 완전 고정. KV 캐시에 상주
[SURVIVAL_CARD]           ← 선택된 카드 1장, 60~120 tok. 세션 내 준고정
[DEVICE_STATE]            ← 요청마다 변함. 아래 §4.1
[USER]                    ← 마지막
```

### 4.1 DEVICE_STATE — 새 도메인의 핵심 (그리고 지연의 함정)

오지 도메인은 장치 상태가 훨씬 많습니다. **다 넣으면 프롬프트가 폭발합니다.**

```
포함 (약 40~60 tok):
  gps: fix|nofix, lat, lon, acc_m, age_s
  time: now, sunset, civil_end, remaining_min
  env: temp_c, humidity_pct, press_hpa, press_trend
  power: pct, days_left
  route: on_trail|off_trail, offset_m, next_wp_m

제외 (프롬프트에 절대 넣지 않음):
  ✗ 전체 GPS 트랙 / 위치 로그 목록
  ✗ 지도 타일 데이터
  ✗ 카드 원문 발췌(original_excerpt) — 화면에만 씀
  ✗ 과거 대화 이력 전체
```

> **기존 문서의 경고가 그대로 유효합니다: 3,300토큰 프롬프트는 prefill만 8초입니다.**
> 오지 도메인은 "상태를 다 넣고 싶어지는" 유혹이 훨씬 큽니다. 60토큰 상한을 지키세요.

### 4.2 출력 스키마

```jsonc
// 역할 1: 분류
{ "scenario_id": "lost" }        // enum 14개. 그게 전부.

// 역할 2: 필드 추출 (route 라벨일 때만)
{
  "target": "basecamp" | "tent" | "trailhead" | "water" | "last_waypoint",
  "ask":    "distance" | "bearing" | "time" | "elevation"
}
// ※ 값은 코드가 계산합니다. 모델은 "무엇을 묻는지"만 지정합니다.

// 역할 3: 카드 다듬기
{ "lines": ["...", "...", "..."] }   // 2~4줄, 각 40자 이내
```

**유지되는 규칙**
- 구조화 출력은 **JSON Schema 제약**으로 강제 (llama.cpp가 GBNF 자동 변환)
- **재시도 없음.** 문법 실패가 구조적으로 0이므로 재요청 단계 불필요
- enum·금지어·출처 ID 존재 여부는 **코드에서** 검증
- 검증 실패 또는 **2초 초과** → 즉시 고정 화면 전환
- `confidence` 필드 없음
- **`temperature = 0`** — 리허설 20회 동일 출력 보장

**신규 규칙 2개**
- **`refuse` 라벨은 스키마가 아니라 키워드 게이트가 먼저 잡습니다.**
  "먹어도 되나 / 식용 / 독버섯 / 이 열매" 등은 모델에 도달하기 전에 코드가 차단합니다.
- **좌표·방위·거리 숫자는 모델 출력 스키마에 존재하지 않습니다.**
  스키마에 필드가 없으면 환각할 자리도 없습니다. 이게 §5-1 계약의 기계적 강제 수단입니다.

## 5. 분류 최적화 — 라벨이 9 → 14로 늘었다

**1차 경로는 여전히 키워드 규칙입니다.** 9-way든 14-way든 20~40토큰 JSON을 생성하는 건 낭비입니다.

```
1차: 키워드 규칙 (즉시, 0 ms)
     "길 / 어디 / 잃"      → lost
     "해 / 어두 / 몇 시"   → daylight
     "추 / 젖 / 떨"        → warmth
     "먹 / 식용 / 버섯"    → refuse   ← 최우선 매칭
2차: 1차 미스 시 LLM 라벨 1개 생성 (0.6 s)
3차: 2차도 unknown → 고정 안내 카드 + 검색(FTS5) 화면
```

**측정해야 할 것**: 14 라벨 혼동 행렬. 특히 `lost` ↔ `route`, `shelter` ↔ `sleep_safety`,
`warmth` ↔ `weather` 3쌍이 붙습니다. `eval/`에 케이스를 넣고 재현 측정하세요.

> **[03](03_beginner_risk_taxonomy.md)의 라벨 정의를 다시 볼 것.** 라벨 수를 늘린 만큼 정확도 검증이 필요합니다.
> 현재 `eval/` 폴더는 **비어 있습니다.** 이번 전환에서 반드시 채워야 합니다.

## 6. TTS — 이번 전환의 최대 신규 리스크

### 6.1 문제

기존 작품에는 음성 출력이 없었습니다. **완전히 새로 만들어야 합니다.**

| 후보 | 한국어 | 라이선스 | CPU 실시간 | 메모리 | 판정 |
|---|---|---|---|---|---|
| **Piper** | ❌ **공식 음성 목록에 없음** `[출처]` | MIT | ✅ (Pi 4에서 실시간) | 수십 MB | ❌ 한국어 불가 |
| **MeloTTS-Korean** | ✅ **있음** | **MIT** | ✅ CPU 실시간 가능 | 1~2 GB `[출처]` | ⭕ **1순위 후보** |
| **Kokoro-82M** | ✅ 지원 언어 9개에 한국어 포함 | **Apache-2.0** | ✅ (GPU RTF 0.03) | 1~2 GB `[출처]` | ⭕ 2순위 |
| espeak-ng | ✅ (규칙 기반) | GPL | ✅ 초경량 | ~10 MB | △ **최후 폴백**. 음질 나쁨 |
| Coqui XTTS-v2 | ✅ | 비상업 제한 | ❌ 무거움 | 큼 | ❌ |

### 6.2 메모리 재계산

TTS가 1~2 GB를 쓰면 기존 예산이 흔들립니다.

| 구성 | 기존 예산 | 신규 추정 |
|---|---|---|
| OS + 데스크톱 | 1.0 | 1.0 |
| Chromium kiosk | 0.8 | **1.2** (벡터 지도 WebGL 렌더링 추가) |
| Python 백엔드 | 0.2 | 0.2 |
| **LLM 상주** | 1.4 | 1.4 |
| STT 온디맨드 | 0.5 | 0.5 |
| **TTS 온디맨드** | — | **0.5 ~ 1.5** |
| **동시 최대** | 4.3 / 6.8 | **4.8 ~ 5.3 / 6.8** `[추정]` |
| 여유 | 2.5 GB | **1.5 ~ 2.0 GB** ⚠️ |

**STT와 TTS를 절대 동시에 올리지 않는다는 전제**에서만 성립합니다.
동시에 올리면 자체 게이트(MemAvailable ≥ 1 GB)를 종이 위에서 실패합니다.
→ **온디맨드 로드/언로드 스케줄러가 필요합니다.** 기존에는 없던 컴포넌트입니다.

### 6.3 즉시 할 일 — W1 스파이크

**TTS 결정을 W3까지 미루면 안 됩니다.** 이번 전환에서 유일하게 "안 될 수도 있는" 항목입니다.

```
W1 스파이크 (2일)
  1. MeloTTS-Korean을 Xavier NX에 올린다
  2. 측정: 모델 로드 시간 / 피크 RSS / RTF / 첫 오디오까지 지연
  3. 판정 기준
       RTF < 0.5  AND  피크 메모리 < 1.0 GB   → 채택
       실패                                    → Kokoro-82M 재시도
       둘 다 실패                              → espeak-ng 폴백 확정 + 보고서에 명시
  4. 결과를 OGTECH-llm/results/ 에 기록
```

## 7. 안전 계약 — LLM 관련 조항 (기계적 강제 수단 포함)

| # | 계약 | **어떻게 강제하나** |
|---|---|---|
| 1 | 경로·방위·거리를 LLM이 생성하지 않음 | **출력 스키마에 숫자 필드를 두지 않음** |

| 5 | 진단·약물·침습 처치 금지 | 금지어 사전 + 코드 후검증 |
| 6 | 2초 초과 시 즉시 고정 화면 | 하드 타임아웃. 재시도 없음 |
| 7 | 모의 값 혼입 시 DEMO 표시 유지 | |
