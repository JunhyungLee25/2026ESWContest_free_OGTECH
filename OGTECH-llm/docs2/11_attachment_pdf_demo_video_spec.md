### 1.2 분석 방법

1. PDF 전체 19쪽을 PNG로 렌더링하고 페이지별 화면과 도형을 직접 판독했다.
2. PDF 텍스트 추출 결과는 한글 본문 대부분이 도형화되어 불완전했으므로 보조 자료로만 사용했다.
3. 영상은 5초 간격 전 구간 프레임, 주요 상태 전환 프레임, 오디오 트랙, 촬영 계획 문서를 교차 확인했다.
4. 영상의 화면 오버레이와 실제 촬영 장면을 분리해서 기록했다. 영상 속 지도 이동은 실제 GPS 트랙이 아니라 영상용 합성 궤적이다 `[출처: 영상 및 촬영 계획]`.
5. 원본에서 보인 동작과 현재 안전 계약에 맞춰 실제로 구현할 동작을 구분했다.

### 1.3 용어

| 용어 | 뜻 |
|---|---|
| 자료 동작 | PDF 또는 영상에 실제로 보이거나 명시된 동작 |
| 구현 동작 | 현재 정본과 안전 계약을 적용해 코드로 만들어야 하는 동작 |
| 고정 카드 | 검수된 문구를 그대로 재생하는 응답. LLM이 절차를 생성하지 않음 |

| 경로 A | 허용된 일반 질문을 분류하고 고정 카드 표현만 2~4줄로 다듬는 경로 |
| 경로 B | 생명·안전 관련 질문을 LLM 없이 고정 카드와 TTS로 바로 보내는 경로 |

## 2. 작품 전체 동작

장치는 오프라인 지도, GPS/GNSS, 환경 센서, CO 감시, 음성 질의응답, 이중 전원 계층을 결합한다. 사용자가 화면을 보고 직접 조작할 수도 있고, 물리 음성 버튼을 눌러 질문하거나 MAP 기능을 제어할 수도 있다.

전체 데이터 흐름은 다음과 같다.

```text
Air530 GNSS ─┐
DHT11 온습도 ├─> STM32H7A3ZI-Q 상시 계층 ─> 검증된 센서 프레임 ─┐
ZE16B-CO     ┘                                              │
                                                             v
음성 버튼 -> 마이크 -> STT -> 안전 키워드 게이트 -> 의도 분류
                                              │
                         ┌────────────────────┴────────────────────┐
                         │                                         │
                  안전 고정 카드                             MAP 명령 계약
                         │                                         │
                         v                                         v
                    오프라인 TTS                    POI/그래프/A*/상태 엔진
                         │                                         │
                         └────────────> 스피커 + 화면 <─────────────┘
```

핵심 원칙은 다음과 같다.

- 센서값은 센서 계층이 만들고, 지도 숫자는 MAP ENGINE이 만든다.
- LLM은 좌표, 방위, 거리, 경로, ETA를 만들지 않는다.
- 생명 관련 절차는 고정 카드만 사용한다.
- GPS fix가 없으면 추측 좌표를 표시하지 않는다.
- 합성값이 하나라도 있으면 화면 전체가 DEMO임을 명확히 표시한다.
- STT, LLM, TTS, 무거운 지도 렌더링은 순차 실행한다.

### 4.1 영상에 나온 고정·동적 음성 문구

| 상황 | 영상 문구 | 구현 방식 |
|---|---|---|
| 베이스캠프 저장 | `베이스캠프가 등록되었습니다.` | 고정 TTS 또는 검수 WAV |
| 물 관련 목적지 후보 | `가장 가까운 지점에 호수가 있습니다. 이곳을 목적지로 지정할까요?` | 검수 POI 이름만 슬롯으로 허용, 마실 수 있다는 판정 금지 |
| 목적지 확인 | `목적지로 설정되었습니다.` | 사용자 확인 후 고정 TTS |
| 목적지 도착 | `목적지에 도착하였습니다.` | 지도 엔진 도착 이벤트 후 고정 TTS |
| 일조 초과 | 영상은 베이스캠프 복귀를 직접 명령 | 현재 구현은 상태·여유율·사전 기준을 알리는 고정 카드로 교체 |
| 베이스캠프 도착 | `Base Camp에 도착하였습니다.` | 지도 엔진 도착 이벤트 후 고정 TTS |
| 야간 모드 | `야간 모드가 활성화되었습니다.` | UI 상태 적용 후 고정 TTS |

## 5. MAP 기능 상세 동작

### 5.1 부팅·초기 상태

1. 정적 HTML/CSS/JS와 로컬 지도 데이터만 읽는다.
2. 네트워크 API, 외부 CDN, 외부 폰트를 호출하지 않는다.
3. 부팅 시 구조 요청 기능이 없고 별도 통신 수단이 필요하다는 경계 고지를 한 번 반드시 표시한다.
4. 지도 데이터, 경로 그래프, POI 사전, 시각, 센서 브리지, 검수된 고정 WAV 파일을 자가진단한다. 동적 TTS 엔진의 로드·청취 품질은 부팅 자가진단 대상이 아니다.
5. 합성값이 있으면 전역 `DEMO` 배지를 표시한다. CO 칸에만 DEMO를 두어 다른 합성값이 실제처럼 보이게 하지 않는다.
6. GPS fix가 없으면 좌표 칸은 회색 `GPS 미수신`으로 표시하고 마지막 확정 좌표의 경과 시간만 보조 표시한다.

### 5.2 상단 글랜서블 상태

현재 정본에서 1초 안에 읽혀야 하는 핵심 4개는 `좌표 상태`, `남은 일조`, `배터리 잔여 일수`, `트레일 이탈 여부`다. PDF/영상의 온습도와 CO도 같은 화면에 유지할 수 있지만 핵심 4개를 밀어내면 안 된다.

| 상태 | 데이터 원천 | 표시 규칙 | 실패 규칙 |
|---|---|---|---|
| 위치·시각 | GNSS + DS3231/시스템 시각 | 지역, KST, fix 상태 | 시각 불확실성 또는 RTC 오류 표시 |
| 남은 일조 | 로컬 일몰/박명 계산 | 남음·주의·부족 단계 | 계산 불가 시 회색 |
| 현재 좌표 | 검증된 GNSS fix | 위도·경도, 정확도 ±m, 위성 수 | 마지막 좌표+age만 표시, 추측 금지 |
| 환경 | 실제 센서 프레임 | 기온·습도·기압, 기상은 `추정` | 센서 미확인 시 회색 |
| CO | STM32 경보 상태 | ppm과 상태 | MAP 프로세스가 경보 발생 주체가 아님 |
| 배터리 | 쿨롱 계측 | 퍼센트보다 현재 페이스의 남은 일수 | 값 미확인 시 회색 |
| 트레일 | 경로 엔진 | 정상·이탈·데이터 없음 | 그래프 없음은 회색 |

### 5.3 목적지 설정

#### 터치 입력

1. 사용자가 `목적지`를 누른다.
2. 지도는 목적지 선택 모드로 바뀐다.
3. 사용자가 지도 지점을 누른다.
4. MAP ENGINE은 터치 좌표에 가장 가까운 보행 그래프 노드를 찾는다.
5. 그래프 스냅 거리가 허용치를 넘거나 경로가 없으면 `경로 데이터 없음`을 회색으로 표시한다.
6. 경로가 있으면 A*로 노드 경로를 구하고 총거리, 초기 방위, ETA를 계산한다.
7. 지도 선과 목적지 마커를 표시한다.

#### 음성 입력

1. 사용자가 음성 버튼을 누른 채 말하고 버튼을 뗀다.
2. STT가 텍스트를 만든다.
3. 안전 게이트가 식용 판정·진단·구조 판단 요청을 먼저 차단한다.
4. 규칙 라우터가 `find_nearest_water` enum과 사용자 확인 필요 상태를 선택한다.
5. LLM 출력에는 좌표·거리·방위 숫자 필드가 없다.
6. 검수 POI 사전에서 후보를 찾는다.
7. 한 후보가 확실하면 이름을 읽고 사용자에게 설정 여부를 묻는다.
8. 사용자가 `예`라고 확인하거나 화면 확인 버튼을 눌러야만 설정한다.
9. MAP ENGINE이 POI의 저장 좌표를 보행망에 스냅하고 경로를 계산한다.

### 5.4 체크포인트

1. 터치 또는 음성 `체크포인트 저장` 명령을 받는다.
2. 현재 GNSS fix가 유효한지 확인한다.
3. 유효하면 시각, 위도, 경도, 정확도, 위성 수, 원천을 런타임 저장소에 기록한다.
4. 유효하지 않으면 저장하지 않고 `현재 위치를 확정할 수 없어 저장하지 못했습니다.` 고정 문구를 낸다.
5. 실제 개인 트랙과 체크포인트는 Git에 들어가지 않는다.

### 5.5 베이스캠프

| 현재 상태 | 입력 | 동작 |
|---|---|---|
| 미등록 | 베이스캠프 버튼/음성 저장 | 유효한 현재 fix를 베이스캠프로 저장 |
| 등록됨, 경로 없음 | 베이스캠프 버튼/음성 경로 표시 | 등록 `waypoint_id`를 MAP ENGINE에 전달 |
| 복귀 경로 표시 중 | 취소 | 경로 오버레이 제거, 저장점은 유지 |
| 베이스캠프 근처 도착 | GNSS 업데이트 | 도착 허용 오차 검사 후 고정 도착 음성 |

### 5.6 경로 계산

```text
입력 좌표 검증
-> 시작/목적 최근접 보행 노드 탐색
-> 수역·장애물·금지 edge 제외
-> A* 탐색
-> 노드 경로와 edge 길이 합산
-> 방위·거리·ETA 계산
-> 검증된 RouteResult 반환
```

- `g(n)`은 출발 노드부터 현재 노드까지 누적 edge 길이다.
- `h(n)`은 현재 노드에서 목적 노드까지의 코드 계산 직선거리다.
- 경로가 없으면 직선으로 대체하지 않는다.
- 방위와 거리는 LLM 프롬프트가 아니라 `RouteResult`에서만 TTS 슬롯으로 들어간다.

### 5.7 위치 갱신과 도착

1. 새 fix의 유효성, 정확도, 시각 순서를 검증한다.
2. 이전 fix보다 오래된 프레임은 버린다.
3. 경로 polyline에 현재 위치를 투영해 남은 경로를 계산한다. 캐시 허용 반경은 정확히 8 m를 포함하며, 8 m를 초과하면 `map_engine`에서 새 현재 위치 기준으로 재경로한다.
4. 자기교차·겹침 polyline에서는 cross-track 거리가 동률일 수 있으므로 그 값만으로 진행량을 고르지 않는다. 후보 진행량의 차이가 크면 캐시를 폐기하고 `map_engine` 재경로로 전환하며, 차이가 작으면 이전 progress를 기준으로 후반 구간을 선택해 disambiguate한다. zero-length polyline은 진행량을 만들지 않는 안전한 경계로 처리한다.
5. 트레일 이탈 임계를 넘으면 지도 이벤트를 만들고 진동·고정 음성 계층에 전달한다.
6. 목적지 허용 오차에 들어오면 한 번만 도착 이벤트를 낸다.

### 5.8 일조 시간

1. 입력은 위도, 경도, 날짜, RTC 시각이다.
2. 인터넷 없이 일몰과 행동 가능 박명 종료를 계산한다.
3. 남은 행동 시간과 코드가 계산한 복귀 예상 시간을 비교한다.
4. 정상·주의·위험 상태를 색과 고정 카드로 표시한다.
5. 영상처럼 LLM이 “돌아가라”고 결정하지 않는다. 사전 등록 기준과 계산 상태를 알려 사용자가 판단하게 한다.
6. 일몰 이후에는 `0분`으로 뭉개지 않고 `N분 초과`를 화면과 TTS에 명시한다. 음수 `remaining_min`은 사용자에게 그대로 읽지 않는다.

### 5.9 야간 모드

1. 터치 또는 음성 `night_on`을 받는다.
2. 화면을 적색 단색 팔레트로 바꾼다.
3. 흰색·시안·앰버 등 주간 팔레트가 남지 않게 한다.
4. `야간 모드가 활성화되었습니다.`를 한 번만 재생한다.
5. 다시 요청하면 해제 여부를 명시적으로 확인하거나 별도 `night_off` 명령으로 처리한다.

### 5.10 CO와 환경

- CO 위험 판정은 STM32가 단독 수행하고, 경보음과 음성 안내는 Jetson 스피커가 낸다(2026-08-31 부저 제거, 향후 재적용 예정).
- MAP은 STM32가 보낸 `normal/caution/alarm/fault` 상태를 화면에 반영한다.
- 센서 확인 없는 `0 ppm`은 정상으로 표시하지 않는다.
- 온습도·기압 상태는 측정 원천과 시각을 함께 보존한다.
- 국지 기상 판정은 항상 `추정` 배지를 단다.

## 6. 음성 질의·MAP 제어 상세 동작

### 6.1 버튼부터 첫 소리까지

```text
물리 버튼 누름
-> 녹음 시작
-> 버튼 뗌
-> 녹음 종료 및 STT 온디맨드 실행
-> 반복 어절/공백 정규화
-> 안전 키워드 게이트
-> MAP 명령 또는 14개 시나리오 분류
-> 고정 카드/지도 결과 선택
-> STT 메모리 해제 확인
-> TTS 온디맨드 실행
-> 첫 문장부터 재생
-> TTS 메모리 해제
```

지연 기준점은 `버튼을 뗀 순간 -> 첫 소리`다. 경로 B는 2.0초 이하, 경로 A는 3.5초 이하가 목표다 `[출처: 정본]`.

### 6.2 허용 MAP 음성 명령

| 명령 ID | 대표 발화 예 | 확인 | MAP 동작 |
|---|---|---|---|
| `save_basecamp` | 여기 베이스캠프로 저장해 | 필수 아님 | 현재 확정 fix 저장 |
| `route_basecamp` | 베이스캠프 경로 보여줘 | 필수 아님 | 저장 waypoint 경로 계산 |
| `save_checkpoint` | 지금 위치 체크포인트로 저장해 | 필수 아님 | 현재 확정 fix 저장 |
| `find_nearest_water` | 근처에 물 있는 곳 있어 | 후보 확인 필요 | 검수 POI 후보 이름만 제시 |
| `confirm_destination` | 거기로 설정해 | 앞선 후보 필요 | POI ID를 목적지로 확정 |
| `reject_destination` | 목적지로 하지 마 | 필수 아님 | pending 후보 취소 |
| `clear_destination` | 목적지와 경로 지워 | 필수 아님 | 현재 목적지와 목적지 경로 제거 |
| `route_destination` | 목적지 경로 보여줘 | 필수 아님 | 저장 waypoint 경로 계산 |
| `route_last_checkpoint` | 최근 체크포인트로 돌아가 | 필수 아님 | 마지막 저장 ID 경로 계산 |
| `status` | 남은 경로·현재 위치·일조 알려줘 | 필수 아님 | MAP 결과를 고정 형식으로 읽음 |
| `night_on` | 야간 모드 켜줘 | 필수 아님 | 적색 단색 모드 |
| `night_off` | 야간 모드 꺼줘 | 필수 아님 | 주간 모드 복귀 |
| `cancel` | 취소 | 필수 아님 | 대기 중인 음성 지도 명령 취소 |

`repeat_response`는 MAP enum이 아니다. Co-LLM의 repeat store v2가 마지막 응답의 `scenario`·`map_action`·`map_status`·`source_id` provenance만 저장하고, 그 provenance로 검수된 고정 문장을 재구성해 다시 재생하는 별도 음성 동작이다. `speech` 원문은 저장하지 않으며 지도 상태를 변경하지 않는다.

### 6.3 LLM MAP 출력 계약

MAP API가 받는 값은 아래와 같은 문자열 enum뿐이다. 현재 구현에서는 자연어를 `RuleRouter`가 먼저 enum으로 바꾸며, LLM이 MAP 좌표·경로 값을 생성하는 경로는 없다.

```json
{
  "action": "find_nearest_water",
  "request_id": "local-request-id"
}
```

금지 필드는 `lat`, `lon`, `bearing`, `distance`, `eta`, `route`, `direction`이다. 음성 API는 `action`과 선택적 `request_id` 외 필드를 거부한다. POI 선택 뒤 좌표는 코드가 로컬 사전에서 조회한다.

### 6.4 다중 의도

1. 식용·진단·구조 판단 차단어가 있으면 다른 명령보다 먼저 `refuse`로 보낸다.
2. MAP 명령이 정확히 하나면 실행한다.
3. 서로 다른 안전 카드가 둘 이상 매칭되면 LLM이 절차를 합성하지 않고 “한 번에 한 요청을 말해 달라”는 고정 문구를 낸다.
4. 안전하지 않은 요청과 MAP 요청이 섞이면 안전 차단을 우선한다.

### 6.5 프롬프트 확장 원칙

“최대한 많은 경우의 수”는 긴 런타임 프롬프트 하나로 넣지 않는다. Xavier에서 프롬프트 길이는 곧 prefill 지연이고, STT 초기 프롬프트는 문장을 베껴 거짓 양성을 만들 수 있다.

경우의 수는 다음 위치에 분산한다.

- 키워드 규칙: 확실한 안전·MAP 명령만 0 ms 분기
- 분류 평가 세트: 말투, 조사, 생략, 오인식, 부정문, 다중 의도 변형
- 검수 카드: 상황별 고정 절차와 허용 문장
- POI 사전: 장소 종류와 별칭
- LLM system prompt: 역할·금지·출력 schema만 짧게 고정
- STT 초기 prompt: 21문장 거짓 양성 0을 유지하는 최소 길이

### 6.6 TTS 품질 계약

영상처럼 깔끔한 음성을 목표로 다음을 지킨다.

6.6.1. 검수된 짧은 고정 경고·도착 문구는 사전 합성 WAV를 우선 사용할 수 있다.
6.6.2. 동적 수치 문장은 MAP ENGINE의 구조화 결과를 고정 템플릿에 끼우고 오프라인 한국어 TTS로 합성한다.
6.6.3. 고품질 엔진을 1순위로 사용하고, 브라우저 Web Speech는 개발 환경 폴백으로만 둔다.
6.6.4. espeak-ng는 알아듣기 어려운 비상 폴백이며 기본 음성으로 쓰지 않는다.
6.6.5. 모든 동적 엔진이 실패하면 검수된 고정 실패 안내 WAV를 한 번만 재생하고 나머지 문장 합성을 중단한다.
6.6.6. 출력은 mono PCM WAV, 일정한 sample rate, clip 없음, 문장 앞뒤 과도한 무음 없음, 일정한 음량을 만족해야 한다.
6.6.7. 문장별 합성과 재생 큐를 사용해 첫 문장을 먼저 들려준다.
6.6.8. STT와 TTS를 동시에 메모리에 올리지 않는다.
6.6.9. 같은 고정 문구는 해시 기반 캐시를 사용해 음색과 발음이 매번 달라지지 않게 한다.
6.6.10. 영어 `Base Camp`, 단위 `ppm`, 방위각, 좌표, 숫자 읽기는 한국어 발음 정규화기를 거친다.
6.6.11. 실패하면 조용히 끝내지 않고 검수된 짧은 폴백 음성을 재생한다.

## 7. 첨부 자료와 현재 정본의 충돌

| 항목 | 첨부 자료 | 현재 구현 기준 | 처리 |
|---|---|---|---|

| CO | ZE16B-CO 표기 | ZE16B-CO 실장 — ZE07-CO / ZE15-CO는 향후 적용 예정(현재 미연결) | STM32 상시 경보 경로 유지 |

| GPS 미수신 | 화면에 명시 없음 | 마지막 확정 좌표+경과 시간, 추측 금지 | 상태 추가 |

| 지도 이동 | 합성 궤적 | 실제 모드는 검증된 GNSS만 사용 | demo/live 모드 분리 |
| 음성 응답 | 일부 브라우저 TTS·사전 WAV | 완전 오프라인 고품질 엔진 + 고정 WAV 폴백 | 엔진 계층 구현 |
| 프롬프트 | 많은 질문 대응 요구 | 60 token DEVICE_STATE와 짧은 고정 prompt | 경우의 수는 테스트·카드로 확장 |
| 구조 요청 | 영상 말미에 별도 장치 지참 | 통신 기능 없음 | 부팅 경계 고지 유지 |

## 8. 구현 범위와 완료 한계

### 8.1 이 작업에서 코드로 구현할 것

- `/video/`: 촬영용 자동 DEMO 화면이다. 장면 전환과 자동 이동은 영상 재현을 위해 합성값을 사용하며, 사용자 확인을 생략할 수 있다.
- `/product/`: 실제 사용자 계약 화면이다. 물 POI 목적지는 사용자 음성 확인 뒤에만 저장하며, 실시간 GPS·센서·MAP 엔진 상태를 사용한다.
- [`MAP/kiosk/live_app.js`](https://github.com/2026-ESW-OGTECH/OGTECH-frontend/blob/main/MAP/kiosk/live_app.js), [`MAP/navigation_service.py`](https://github.com/2026-ESW-OGTECH/OGTECH-frontend/blob/main/MAP/navigation_service.py): 실제 제품 화면 상태, demo/live 분리, 목적지·체크포인트·베이스캠프·야간 모드, 일조 경고, 음성 명령 수신, MAP 결과 읽기, 접근성·상태 이벤트
- `Co-LLM`: STT 후 안전 게이트, 14개 시나리오와 MAP 명령 분류, 검수 카드, MAP command schema, TTS 엔진 선택·정규화·캐시·큐, 통합 실행 루프
- 두 폴더 사이의 로컬 JSON 계약과 오프라인 통합 테스트

### 8.2 소프트웨어만으로 완료할 수 없는 것

- 실제 Air530 수신 성능과 GPS 정확도
- STM32 단독 CO 판정과 Jetson 전원 OFF 상태 지속 감시(그 구간의 소리는 부저 실장 후)
- 물리 버튼, 진동, 부저, 스트로브
- 330 Wh 배터리 14일 운용, MPPT 충전, 실제 전력 게이팅
- 최종 스피커·마이크의 방수와 음질

이 항목은 인터페이스와 시뮬레이션 테스트는 만들 수 있지만 실제 하드웨어 검증 전에는 완료로 표시하지 않는다.

## 9. 계획 -> 수행 -> 검증 -> 피드백 루프

### 루프 1: 기준선

- 계획: 현재 MAP/Co-LLM 구조와 테스트 조사
- 수행: 기존 테스트 실행, 미커밋 변경 보존
- 검증: 실패 목록과 기능 공백 기록
- 피드백: 최소 변경 단위로 구현 순서 재정렬

### 루프 2: MAP 상태와 조작

- 계획: 터치 기능과 상태 머신을 테스트로 먼저 고정
- 수행: 목적지, 체크포인트, 베이스캠프, 일조, 야간 모드 구현
- 검증: 브라우저 없이 가능한 JS/Python 단위 테스트와 1024×600 렌더 확인. 이동 경로는 8 m 캐시 경계와 작은 진행량을 함께 검사한다.
- 피드백: 잘못된 색, DEMO, GPS 실패 상태 수정

### 루프 3: 음성 MAP 제어

- 계획: 허용 명령 schema와 확인 정책 고정
- 수행: STT 텍스트 -> command -> MAP event -> 응답 연결
- 검증: 말투·부정문·다중 의도·오인식 사례 테스트
- 피드백: 거짓 실행을 줄이고 미확실 입력은 확인으로 전환

### 루프 4: TTS

- 계획: 설치 가능한 오프라인 엔진과 폴백 우선순위 결정
- 수행: 전처리, 문장 큐, 캐시, 재생 취소, 고정 WAV 구현
- 검증: 파일 구조, clipping, 무음, sample rate, 문장 순서, 실패 폴백 테스트
- 피드백: 발음 사전과 숫자 읽기 수정

### 루프 5: 통합

- 계획: 영상 장면 1~7과 음성 명령을 자동 시나리오로 작성
- 수행: 상태 전이를 연속 재생
- 검증: `Co-LLM/eval/results/video_scenario_20.json`으로 10단계 `20/20`, 외부 네트워크 `0`, 최악 `258.69 ms`, 고정 도착 TTS `20/20`, `configured_engine_failure_fallback_runs`에 해당하는 **하네스에 구성된 테스트 엔진 전부 실패 고정 fallback `20/20`**을 확인한다. 이는 실제 MeloTTS/Piper/espeak 로드·청취 실증이 아니다 `[미검증]`.
- 피드백: 한 번이라도 잘못된 안전 상태가 나오면 원인 수정 후 20회 재시작

## 10. 소프트웨어 인수 기준

### 10.1 MAP

- [x] 오프라인 상태에서 정적 자산과 로컬 데이터만으로 열린다.
- [x] 전역 DEMO와 live 상태를 혼동하지 않는다.
- [x] GPS fix 없음, 오래된 fix, 낮은 정확도를 구분한다.
- [x] 좌표에 정확도와 위성 수가 함께 표시된다.
- [x] 터치 목적지는 보행망에 스냅하고 경로 없음 상태를 처리한다.
- [x] 체크포인트와 베이스캠프는 유효 fix에서만 저장된다.
- [x] 경로 숫자는 MAP ENGINE에서만 나온다.
- [x] 일조 상태가 정상·주의·위험으로 전이한다.
- [x] 야간 모드는 적색 단색이며 터치·음성으로 제어된다.
- [x] 사용자 조작 대상은 80 px 이상, 본문은 20 px 이상이다.

### 10.2 음성·LLM

- [x] 14개 시나리오와 MAP 명령을 구분한다.
- [x] `refuse`가 다른 명령보다 우선한다.
- [x] LLM schema에 지도 숫자 필드가 없다.
- [x] 안전 경로는 LLM을 우회한다.
- [x] MAP 후보 설정은 사용자 확인 없이는 실행되지 않는다.
- [x] STT와 TTS가 동시에 적재되지 않는다.
- [x] TTS 실패 시 검수된 폴백이 나온다.
- [x] 고정 문구는 반복 재생 때 동일하다.
- [ ] STT 초기 prompt는 21문장 거짓 양성 0을 통과해야 한다.
- [x] LLM 종료 시 고정 카드와 MAP 기본 조작이 유지된다.

### 10.3 영상 재현 시나리오

1. 베이스캠프 저장
2. `아 너무 목마른데` 발화
3. 물을 마셔도 된다고 판정하지 않고 검수 POI 후보만 제시
4. 사용자 확인
5. MAP ENGINE 목적지·경로 계산
6. 이동 상태에서 방위·남은 거리·ETA 갱신
7. 목적지 도착 고정 음성
8. 일조 임계 경고와 베이스캠프 경로 표시
9. 베이스캠프 도착 고정 음성
10. 음성으로 야간 모드 활성화

이 시나리오를 자동화 환경에서 반복 실행하고, 실제 하드웨어에서는 정본의 8개 데모 성공 조건을 별도로 연속 20회 검증한다.

자동 시나리오 결과 증거: [`Co-LLM/eval/results/video_scenario_20.json`](../Co-LLM/eval/results/video_scenario_20.json). 브라우저 결과 증거는 `MAP/test-results/product_ui_1024x600.json` (로컬 산출물, 저장소에 커밋하지 않음)이다. 두 결과는 소프트웨어·시뮬레이션 인수 결과이며 실제 Jetson 청취, STT 21문장, STM32/CO/GPIO, 실기 20회 완료를 뜻하지 않는다.
