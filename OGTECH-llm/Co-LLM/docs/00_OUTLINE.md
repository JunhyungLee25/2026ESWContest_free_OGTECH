## 5. 결과 및 분석

- 5.1 [단계 분해표를 제시하는 내용 — load / mel / encode / sample / batchd]
- 5.2 [`load time`이 디스크 I/O가 아니라 CUDA 컨텍스트 초기화임을 증명하는 내용 — 페이지 캐시가 더워져도 안 줄어든 관측을 근거로]
- 5.3 [GPU encode가 연산량에 둔감함을 보이는 내용 — 파라미터 1/3, 컨텍스트 절반에도 encode가 거의 안 줄어든 관측]
- 5.4 [따라서 이 워크로드에서 GPU는 순손실이라는 결론을 도출하는 내용]
- 5.5 [기각한 가설들을 정직하게 나열하는 내용 — FA가 느릴 것, PulseAudio가 PCM을 점유했을 것, espeak-ng가 장치를 잡았을 것]
- 5.6 [측정 없이 판단했다면 내렸을 오답을 대비시키는 내용 — "GPU가 있으니 GPU를 쓴다"]

## 6. 설계 결정 — 최적점 선정

- 6.1 [최적성 기준을 정의하는 내용 — 하드 게이트 4개와 최적화 목표 2개, 동점 시 우선순위]
- 6.2 [후보 구성별 점수표를 제시하는 내용]
- 6.3 [선정 구성과 그 근거를 적는 내용]
- 6.4 [**보드를 교체하지 않는 이유**를 적는 내용 — "GPU가 졌으니 SBC를 바꾸자"는 반론에 답하는 절]
  - 6.4.1 [GPU가 진 조건을 한정하는 내용 — 74M 파라미터에서는 커널 오버헤드 > 연산량. 크기 의존적 결과이지 GPU 무용론이 아님]
  - 6.4.2 [LLM은 1.5B로 20배 크고 `prefill 413 tok/s [실측]`가 GPU 경로의 산물임을 적는 내용]
  - 6.4.3 [RPi 5로 가면 STT는 개선 가능하나 LLM이 CPU 전용이 되어 경로 A 3.5초 예산이 붕괴함을 적는 내용]
  - 6.4.4 [일정·동결 제약을 적는 내용 — 하드웨어 동결, 내부 동결 2026-09-01, 부팅매체·전원게이팅·STM32 연동·외함 재작업]
  - 6.4.5 [**결론은 "작업 크기에 따라 최적 실행 타깃이 다르다"이며, 그래서 한 보드에 CPU·GPU가 같이 있는 편이 유리하다**는 내용]
- 6.5 [`00_frozen_decisions.md`에 동결할 항목을 명시하는 내용 — whisper 실행 옵션, 백엔드, 클럭 정책]
