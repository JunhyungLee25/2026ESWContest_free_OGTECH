## 0. 초록

배낭 장착형 오프라인 생존 보조 장치는 화면이 기본 OFF이므로 음성이 1차 출력이다.
음성 질의는 STT → 분류 → 고정 카드 → TTS 경로를 지나며, 생명 관련 질의는 LLM을 우회해
**2.0초 안에** 소리가 나와야 한다. 본 실험은 이 예산 안에 들어가는 STT 구성을 찾기 위해
Jetson Xavier NX에서 whisper.cpp를 8개 축으로 분해 측정했다.

핵심 결과는 반직관적이다.

1. **이 워크로드에서 GPU는 지연과 에너지 양쪽에서 순손실이다.** CPU 대비 지연 2.4배,
   질의당 에너지 1.27배다 `[실측]`. 원인은 연산 성능이 아니라 질의마다 반복되는
   CUDA 컨텍스트 초기화(약 1.6초)와, 74M 파라미터 모델에서 커널 실행 오버헤드가
   연산량을 압도하는 구조다.
2. **모델을 키워도 정확도가 오르지 않았다.** whisper small은 base보다 3.7배 느린데
   키워드 게이트 통과율이 같았고, 오히려 `이 물`을 `이불`로 잘못 인식해
   **다른 라벨의 키워드를 만들어내는** 더 위험한 오류를 냈다 `[실측]`.
3. **중앙값으로 판정하면 틀린다.** 데모 성공 조건이 연속 20회이므로 판정 지표는
   최댓값이어야 한다. 중앙값 1위 구성(983 ms)의 최댓값은 12,602 ms였다 `[실측]`.
4. **최댓값을 망친 원인은 무음 구간의 디코더 반복 루프였다.** 1.15초 발화를 담은
   5초 파일에서 디코드 스텝이 219회로 폭주했고, VAD로 무음을 제거하자 5회로 줄었다 `[실측]`.

측정 없이 판단했다면 "GPU가 있으니 GPU를 쓰고, 정확도가 부족하면 모델을 키운다"는
결론에 도달했을 것이다. 세 판단이 모두 반대였다.

## 1. 서론

### 1.1 왜 음성이 1차 출력인가

본 작품은 14일 연속 운용을 전제로 하며, 전력 예산이 330 Wh로 고정되어 있다.
7인치 화면을 켜는 데 13 W가 들기 때문에 화면은 기본 OFF이고, 사용자는 화면을 보려면
배낭에서 장치를 꺼내야 한다. 따라서 **음성이 1차 출력, 화면이 2차 출력**이다.

음성 질의는 물리 버튼으로 시작하고 버튼을 뗀 순간 응답이 시작되어야 한다.

### 1.2 세 겹의 제약

| 축     | 제약                                                     | 출처              |
| ------ | -------------------------------------------------------- | ----------------- |
| 지연   | 경로 B ≤ 2.0 s / 경로 A ≤ 3.5 s                        | `00_frozen_decisions.md` §4 |
| 메모리 | 6.8 GB 중 STT는**온디맨드 0.5 GB 이내**, 상주 금지 | `00_frozen_decisions.md` §2 |
| 전력   | S4 응답 구간 18 W × 100 s/일 = 500 mWh/일               | `00_frozen_decisions.md` §2 |

세 축은 서로 맞바꿀 수 있는 관계가 아니다. 지연은 사용자 체감이고, 메모리는 LLM 상주와
경합하며, 전력은 14일 운용의 성립 조건이다.

### 1.3 STT가 구조적으로 필수인 이유

STT는 "음성을 텍스트로 바꾸는 편의 기능"이 아니라 **안전 계약을 걸 수 있게 만드는 장치**다.

```
음성 → [STT] → 텍스트 → [키워드 게이트 · 검증 · 카드 치환] → 텍스트 → [TTS] → 음성
                   ↑
           안전 장치가 걸리는 유일한 지점
```

텍스트 중간 표현이 없으면 다음이 전부 갈 곳을 잃는다.

- `먹/식용/버섯 → refuse` 키워드 매칭 (안전 계약 6)
- 생명 관련 라벨을 LLM 앞에서 잘라내는 경로 B 분기 (안전 계약 2)
- 검수된 고정 카드로의 치환 (안전 계약 5)
- 좌표·방위·거리 필드를 스키마에서 제거하는 기계적 강제 (안전 계약 1)

음성을 직접 입력받는 멀티모달 모델(Qwen3-Omni 계열 등)은 더 빠르고 자연스럽지만
**검수 지점이 0개**다. `00_frozen_decisions.md` §2가 멀티모달을 제외한 이유는 메모리 예산이 표면적 근거이고,
안전 계약과의 충돌이 더 근본적인 이유다.

### 1.4 기여

1. Jetson Xavier NX에서 whisper.cpp의 단계별 지연을 분해하고, `load time`의 정체가
   디스크 I/O가 아니라 CUDA 컨텍스트 초기화임을 증명했다.
2. 74M 파라미터 규모의 워크로드에서 **GPU가 CPU보다 느리고 에너지도 더 쓴다**는 것을
   지연·전력 동시 측정으로 보였다.
3. 최댓값 기준 판정이 중앙값 기준 판정과 다른 결론을 낸다는 것을 보이고,
   그 원인인 디코더 반복 루프를 디코드 스텝 수로 규명했다.
4. 이 결과를 `00_frozen_decisions.md`에 반영할 실행 구성 후보와 미결 항목으로 정리했다.

## 2. 배경 및 관련 연구

### 2.1 엣지 추론의 실행 타깃 선택

엣지 기기에서 추론을 **어디서 실행할지** 고르는 문제는 독립된 연구 축이다.

- **Neurosurgeon** — 신경망을 계층 단위로 쪼개 일부는 기기에서, 일부는 서버에서 실행하는
  분할 지점을 선택한다.
- **AutoScale** — 강화학습으로 실행 타깃(CPU/GPU/가속기/클라우드)을 **런타임에 동적으로**
  고른다. 보상 함수는 에너지를 주 항으로 두고 지연·정확도를 가중치 α, β로 더한다.

두 연구 모두 "최적 실행 타깃은 워크로드와 상태에 따라 달라진다"를 전제로 한다.

### 2.2 본 작업과의 차이

|           | AutoScale                       | 본 작업                                    |
| --------- | ------------------------------- | ------------------------------------------ |
| 선택 시점 | 런타임, 매 추론마다             | **정적, 배포 전 1회**                |
| 방법      | 강화학습 정책                   | **오프라인 실측 후 수동 선택**       |
| 대상      | 다양한 워크로드·상태           | **단일 워크로드, 단일 기기**         |
| 목적함수  | 에너지 우선 + 지연·정확도 가중 | **지연 하드 게이트 + 에너지 최소화** |

본 작업은 훨씬 국소적이다. 다만 **"측정하기 전에는 어느 타깃이 유리한지 알 수 없다"**는
문제의식은 동일하며, 실제로 직관과 반대되는 결과가 나왔다.

### 2.3 whisper의 구조와 30초 창

whisper는 인코더-디코더 구조다. 인코더는 mel 스펙트로그램을 고정 길이 컨텍스트로 변환하는데,
기본값은 `n_audio_ctx = 1500`이며 이는 **30초에 해당**한다. 3초를 말하든 11초를 말하든
인코더는 30초 분량을 계산한다.

whisper.cpp는 `-ac N`으로 이 컨텍스트를 줄일 수 있다. 1단위 ≈ 20 ms이므로
`-ac 450`은 9초 창이다. 다만 창을 지나치게 줄이면 디코더가 발산한다(§5.5).

디코더는 자기회귀 방식이라 생성 토큰 수만큼 스텝이 든다. **무음 구간에서 마지막 세그먼트를
반복 생성하는 실패 모드**가 알려져 있으며, 본 실험에서 이것이 최댓값을 지배했다.

### 2.4 Xavier NX의 클럭 정책

Jetson은 `nvpmodel`로 전력 모드를, `jetson_clocks`로 클럭 고정을 제어한다.
`jetson_clocks`는 CPU 거버너를 `performance`로 바꾸고 GPU/EMC 클럭을 최대로 고정하며,
**재부팅 전까지 유지**된다. 복원하려면 사전에 `--store`로 스냅샷을 저장해야 한다.

이 동작이 측정을 오염시킨 사례가 있다(§5.7).

### 3.3 측정 방법

| 측정 대상   | 도구                                                | 산출                                                   |
| ----------- | --------------------------------------------------- | ------------------------------------------------------ |
| 단계별 지연 | `whisper_print_timings`                           | load / mel / sample / encode / decode / batchd / total |
| 전력        | `tegrastats --interval 200`, `VDD_IN` 레일      | 유휴 평균, 활성 평균, 피크                             |
| 열          | `/sys/devices/virtual/thermal/thermal_zone*/temp` | 실행 종료 시점 온도                                    |
| 정확도      | 키워드 게이트 통과 여부                             | 6발화 중 통과 수                                       |

**질의당 에너지**는 다음과 같이 계산했다.

```
mWh/질의 = (활성 평균 mW − 유휴 평균 mW) × 배치 벽시계 초 ÷ 3600 ÷ 질의 수
```

유휴를 차감하는 이유는, 측정하려는 것이 **워크로드에 귀속되는 추가 에너지**이기 때문이다.
피크 W는 순간값이라 배터리 수명과 직결되지 않는다.

## 4. 실험

각 실험은 `가설 → 조작 변인 → 측정 → 결과 → 판정` 형식으로 기술한다.

### E0. 오디오 배관 성립

- **가설**: USB 오디오 장치는 디바이스 트리 작업 없이 ALSA 카드로 인식된다.
- **조작 변인**: 없음 (성립성 확인)
- **결과**: 인식·재생 모두 성공. 다만 `plughw:` 배타 접근에서 간헐적으로 `Device or resource busy`가 발생했다.
- **판정**: 성립. EBUSY는 재현되지 않았고 근본 원인 미확정. `default` 폴백을 스크립트에 넣어 우회했다.

`fuser -v /dev/snd/*`에서 PulseAudio가 잡고 있던 것은 `controlC*`(믹서 컨트롤)뿐이었고
재생 스트림 `pcmC*D*p`는 비어 있었다 `[실측]`. 핫플러그 직후 프로파일 탐색 창이 가장 유력한
설명이나 현행범을 확보하지 못했다.

### E1. 빌드 구성

- **가설**: CUDA 아키텍처를 고정하고 ARM ISA 확장을 명시하면 빌드 시간과 CPU 성능이 개선된다.
- **조작 변인**: `CMAKE_CUDA_ARCHITECTURES`, `GGML_NATIVE`, `GGML_CPU_ARM_ARCH`
- **결과**:
  - `nvcc`가 PATH에 없어 CUDA 백엔드 구성이 실패했다. JetPack이 `/usr/local/cuda/bin`을 PATH에 넣지 않는다.
  - `GGML_CPU_ARM_ARCH`만 주면 무시된다. `GGML_NATIVE`(기본 ON)가 native 경로를 우선한다.
  - GCC 9.4는 `-mcpu=native`로 Carmel을 인식하지 못해 `HAVE_DOTPROD`, `HAVE_FP16_VECTOR_ARITHMETIC`이 모두 `Failed`였다.
  - `-DGGML_NATIVE=OFF -DGGML_CPU_ARM_ARCH=armv8.2-a+fp16+dotprod`로 둘 다 `Success`.
- **판정**: 두 플래그를 함께 주는 것이 필수.

### E2. DVFS·클럭 정책

- **가설**: `jetson_clocks`로 클럭을 고정하면 짧은 작업의 지연이 개선된다.
- **조작 변인**: `jetson_clocks` 적용 여부
- **측정**: jfk.wav(영어 11초, GPU) 및 한국어 6발화(CPU)
- **결과**:

| 경로               | 클럭 미고정 | 클럭 고정 | 변화                               |
| ------------------ | ----------: | --------: | ---------------------------------- |
| GPU encode (jfk)   |   18,173 ms |  2,933 ms | **6.2배 개선** `[실측]`    |
| CPU 중앙 지연 (ko) |    1,582 ms |  1,577 ms | **0.3% (노이즈)** `[실측]` |
| CPU 질의당 에너지  |    2.31 mWh |  2.35 mWh | 차이 없음`[실측]`                |

- **판정**: **6.2배 이득은 GPU 경로 전용이다.** CPU 경로에서는 효과가 없다.
  `schedutil` 거버너도 지속 부하에서 최대 클럭까지 올라가기 때문으로 보인다 `[추정]`.

### E3. 디코딩 파라미터

- **가설**: 기본 빔서치(5빔, best-of 5)는 짧은 발화에 과하다.
- **조작 변인**: `-bo`, `-bs`
- **결과**: jfk.wav GPU 기준 total 10,258 → 5,223 ms `[실측]`. 인식 결과 동일.
- **판정**: `-bo 1 -bs 1` 채택. 이후 모든 실험에 적용.

### E4. FlashAttention

- **가설**: Volta(7.2)에서 FlashAttention 커널이 최적화되지 않아 느릴 수 있다.
- **조작 변인**: `-nfa`
- **결과**: encode 2,443 → **3,285 ms**로 34% 악화 `[실측]`.
- **판정**: **가설 기각.** FlashAttention은 켜 두는 것이 이득.

### E5. 오디오 컨텍스트

- **가설**: 발화가 짧으므로 인코더 컨텍스트를 줄이면 비례해서 빨라진다.
- **조작 변인**: `-ac 600 / 450 / 300`
- **결과**:

| 구성                       |   encode | 중앙 지연 |    **최댓값** | 인식 품질      |
| -------------------------- | -------: | --------: | ------------------: | -------------- |
| `-ac 600` (CPU, `-nf`) | 1,190 ms |  1,568 ms |            3,786 ms | 양호           |
| `-ac 450` (CPU, `-nf`) |   875 ms |  1,244 ms |            3,363 ms | **최상** |
| `-ac 300` (CPU)          |   592 ms |    983 ms | **12,602 ms** | **환각** |

`-ac 300`의 인식 결과 예:

```
#1  여기 가 오디야Er
#3  ()] 오늘 밤 얼마 하나 추워줘 builder dayacular 벅 squares.. hm-hein melt Anda!
```

- **판정**: `-ac 450` 채택, `-ac 300` 기각. GPU 경로에서는 `-ac`가 거의 효과가 없었다
  (2,443 → 2,547 ms) `[실측]` — E7의 근거가 된다.

### E6. 모델 크기

- **가설**: 큰 모델이 한국어 정확도에서 유리하다.
- **조작 변인**: `ggml-base.bin` ↔ `ggml-small.bin`
- **결과**:

| # | 실제 발화                   | small (CPU)                  | base (CPU)                  |
| - | --------------------------- | ---------------------------- | --------------------------- |
| 1 | 여기가 어디야               | 여기가 어디야?               | 여기가 어디야               |
| 2 | 해 지기 전에 돌아갈 수 있어 | 해지기 전에…                | 해**치**기 전에…     |
| 3 | 오늘 밤 얼마나 추워져       | ✓                           | ✓                          |
| 4 | 이 물 마셔도 돼             | **이불** 마셔도 돼     | 이**물**을 마셔도 돼  |
| 5 | 텐트 어디에 쳐야 돼         | 텐트 어디에**춰**야 돼 | 텐트 어디에**저**야돼 |
| 6 | 이 버섯 먹어도 돼           | ✓                           | ✓                          |

지연은 small 5,857 ms vs base 1,582 ms로 **3.7배 차이** `[실측]`.

- **판정**: **가설 기각.** 키워드 게이트 통과율이 6/6으로 동일하고, small의 `#4`는
  `물`을 잃은 데다 **`이불`이라는 다른 라벨(침구·`sleep_safety`)을 연상시키는 단어를 생성**했다.
  더 느리면서 더 위험하다.

### E7. 실행 타깃 — 본 문서의 핵심

- **가설**: GPU가 있으니 GPU가 빠르다.
- **조작 변인**: `-ng` (GPU 비활성)
- **결과**:

|                |                GPU |                CPU | 비         |
| -------------- | -----------------: | -----------------: | ---------- |
| load (중앙)    |           1,590 ms |   **180 ms** | 8.8배      |
| encode (중앙)  |           2,066 ms |   **916 ms** | 2.3배      |
| 총지연 (중앙)  |           3,805 ms | **1,385 ms** | 2.7배      |
| 질의당 에너지  |           2.94 mWh | **1.22 mWh** | 2.4배      |
| 순간 활성 전력 | **5,415 mW** |           6,634 mW | GPU가 낮음 |
| 피크 전력      |          11,257 mW | **7,518 mW** | GPU가 높음 |

- **판정**: **가설 기각.** CPU가 지연·에너지 양쪽에서 우세하다.

### E8. 전력·에너지

- **가설**: 전력이 구속 조건이므로 에너지를 최소화하는 구성이 최적이다.
- **결과**: 최적 구성에서 질의당 1.22 mWh `[실측]`. `00_frozen_decisions.md` §2 S4 예산은 500 mWh/일이므로
  **하루 약 410회 질의까지 예산 안**이다 `[추정]`.
- **판정**: **전력은 구속 조건이 아니다.** 실사용에서 하루 400회 음성 질의는 발생하지 않는다.
  구속 조건은 지연이다. 이 판정이 §6의 기준 설계를 바꿨다.

### E9. 열

- **결과**: 6질의 배치 종료 시점 CPU 온도가 36.5 ~ 44.0 °C 범위 `[실측]`.
  가장 높은 값은 GPU·클럭 고정 구성, 가장 낮은 값은 최적 CPU 구성이었다.
- **판정**: 스로틀 임계와 거리가 멀다. 다만 **20회 연속 지속 부하는 미측정**이므로
  데모 조건에서의 열 거동은 확인이 남아 있다.

### E10. 한국어 정확도

- **지표**: 키워드 게이트 통과율. WER이 아니다(§6.2).
- **결과**: 측정한 9개 구성 전부 **6/6** `[실측]`.
- **판정**: 이 지표만으로는 구성을 가를 수 없다. 인식 텍스트를 직접 비교해야 하며(E6),
  지표 보강이 필요하다(§6.4).

### E11. 반복 루프 규명

- **가설**: `#1` 발화만 4배 느린 것은 temperature fallback 때문이다.
- **조작 변인**: `-nf`(fallback 비활성), `-mc 0`(컨텍스트 이월 차단), `-sns`(비발화 토큰 억제), `--vad`
- **결과** (`ko_1.wav` 단독, 발화 1.15초 / 파일 5.0초):

| 구성           | fallbacks | decode                        | encode |              total | 출력      |
| -------------- | --------- | ----------------------------- | -----: | -----------------: | --------- |
| 기본(`-nf`)  | 0 p / 0 h | **1,821 ms / 219 runs** | 850 ms |           3,263 ms | 44회 반복 |
| `-mc 0 -sns` | 0 p / 0 h | 1,852 ms / 219 runs           | 766 ms |           3,250 ms | 44회 반복 |
| `--vad`      | 0 p / 0 h | **42 ms / 5 runs**      | 722 ms | **1,202 ms** | 정상      |

VAD는 80,000 → 18,400 샘플로 **77% 감소**시켰고, 검출된 발화 구간은 0.83 ~ 1.98초였다 `[실측]`.

- **판정**: **가설 기각.** `fallbacks = 0`이므로 fallback이 아니다.
  원인은 **무음 구간의 디코더 반복 생성**이며, 디코더 측 완화책(`-mc`, `-sns`)은 무효했다.
  입력에서 무음을 제거하는 것만이 유효했다.

### E12. 무음 길이 의존성 — 미측정

- **가설**: 반복 루프는 5초 고정 녹음이라는 **측정 하네스의 산물**이며,
  버튼을 누르는 동안만 녹음하는 제품 조건에서는 발생하지 않는다.
- **계획**: 3초 녹음으로 6발화를 재수집하고 VAD 유무 두 구성을 비교한다.
- **의의**: 가설이 맞으면 VAD 없이 정확도 1위 구성(`-ac 450 -nf`)을 쓸 수 있다.

### E13. TTS 명료도 — 진행 중

- espeak-ng 한국어: 합성 약 60 ms `[실측]`, 그러나 **청취자가 내용을 알아듣지 못했다** `[실측]`.
- Piper·MeloTTS 미측정. `00_frozen_decisions.md` §10 미결 항목 #2가 열려 있다.
- 후보로 올라 있던 Kokoro-82M은 한국어 지원 여부가 확인되지 않았다 `[미검증]`.

### E14. 게이트 정밀도·`refuse` 누락률 — 미착수

## 5. 결과 및 분석

### 5.1 단계 분해

최적 구성(base / CPU / `-ac 450 -nf --vad`)의 단계별 중앙값 `[실측]`:

```
load     180 ms    모델 파일 읽기
mel       18 ms    스펙트로그램
VAD      125 ms    무음 제거
encode   916 ms    인코더        <- 지배적
decode    42 ms    디코더
------------------------------
total   1385 ms
```

지연의 66%가 인코더다. 인코더는 `-ac`로 창을 줄이는 것 외에 손댈 여지가 적다.

### 5.2 `load time`은 디스크 I/O가 아니다

GPU 경로에서 `load time`이 1,882 ms → 1,895 ms로 **페이지 캐시가 더워져도 줄지 않았다** `[실측]`.
487 MB를 캐시에서 읽는다면 0.2초대여야 한다.

`-ng`로 GPU를 끄자 **382 ms**로 떨어졌다 `[실측]`.

**정체는 CUDA 컨텍스트 초기화와 모델 GPU 업로드다.** 그리고 이것은 프로세스마다 새로 낸다.
서브프로세스로 STT를 호출하는 구조에서는 질의마다 이 비용이 반복된다.

이 발견은 초기 판단을 뒤집었다. 애초에 CLI 서브프로세스 방식을 고른 이유는
"프로세스가 끝나면 커널이 메모리를 회수하므로 `STT는 온디맨드 로드/언로드` 규칙을 공짜로
지킨다"는 것이었다. **GPU를 쓰면 그 공짜의 대가가 질의당 1.6초로 돌아온다.**
CPU 백엔드에서는 그 대가가 0.18초로 줄어 원래의 장점이 유지된다.

### 5.3 GPU encode는 연산량에 둔감하다

| 조작                | 연산량 변화  | encode 변화                             |
| ------------------- | ------------ | --------------------------------------- |
| small → base       | 파라미터 1/3 | 2,443 → 2,135 ms (**13% 감소**)  |
| `-ac` 1500 → 600 | 컨텍스트 40% | 2,443 → 2,547 ms (**변화 없음**) |

연산량을 3분의 1로 줄여도 13%만 빨라진다는 것은 **연산이 병목이 아니라는 뜻**이다.
커널 실행 오버헤드와 낮은 점유율이 지배한다 `[추정]`. 이 크기의 모델에 Xavier GPU는 과분하다.

같은 조작을 CPU에서 하면 비례해서 줄어든다 — `-ac 600 → 450`에서 encode 1,190 → 875 ms(26% 감소) `[실측]`.

### 5.4 race-to-idle

GPU는 **순간 전력이 더 낮다**(활성 5,415 vs CPU 6,634 mW) `[실측]`.
그런데 질의당 에너지는 더 크다(2.94 vs 1.22 mWh).

```
에너지 = 전력 × 시간
GPU:  낮은 전력 × 긴 시간   =  큰 에너지
CPU:  높은 전력 × 짧은 시간 =  작은 에너지
```

배터리 수명을 논할 때 **피크 W를 지표로 삼으면 정확히 반대 결론에 도달한다.**
지표는 질의당 에너지여야 한다.

### 5.5 `-ac 300`이 환각을 낳은 이유

인코더 창이 6초인데 녹음이 5초라 여유가 거의 없었다. 잘린 표현을 받은 디코더가 발산했고,
`#1`과 `#3`에서 각각 12.6초, 10.8초가 걸렸다.

주목할 점은 **키워드 게이트는 6/6으로 통과했다**는 것이다.
`오늘 밤 얼마 하나 추워줘 builder dayacular…`에 `추워`가 우연히 포함됐기 때문이다.
지표가 통과시켰다고 해서 쓸 수 있는 출력은 아니다(§6.4).

### 5.6 최댓값이 중앙값과 다른 결론을 낸다

| 구성                  |           중앙값 |             최댓값 | 중앙값 순위   | 최댓값 순위   |
| --------------------- | ---------------: | -----------------: | ------------- | ------------- |
| `-ac 300`           | **983 ms** |          12,602 ms | **1위** | 최하위        |
| `-ac 450 -nf`       |         1,244 ms |           3,363 ms | 2위           | 4위           |
| `-ac 450 -nf --vad` |         1,385 ms | **1,495 ms** | 4위           | **1위** |

**데모 성공 조건이 연속 20회이므로 판정 지표는 최댓값이다.**
중앙값 1위 구성을 골랐다면 20회 중 여러 번 실패했을 것이다.

VAD는 중앙값을 141 ms 늘리는 대신 최댓값을 1,868 ms 줄였다. VAD 자체 비용이 125 ms이므로
**순수하게 그만큼만 손해 보고 꼬리를 잘라낸 것**이다. 에너지도 1.48 → 1.22 mWh로 내려갔는데,
폭주 디코딩이 사라졌기 때문이다.

### 5.7 기각한 가설과 측정 하네스의 오염

| 가설                                        | 판정 | 근거                                        |
| ------------------------------------------- | ---- | ------------------------------------------- |
| Volta에서 FlashAttention이 느릴 것          | 기각 | 끄니 34% 악화                               |
| 모델을 줄이면 GPU도 비례해 빨라질 것        | 기각 | base로 줄여도 13%만 감소                    |
| `load time`은 디스크 읽기일 것            | 기각 | 페이지 캐시가 더워져도 불변                 |
| `#1` 지연은 temperature fallback일 것     | 기각 | `fallbacks = 0 p / 0 h`                   |
| 디코더 측 완화책으로 반복을 막을 수 있을 것 | 기각 | `-mc 0 -sns`에서 219 runs 그대로          |
| 전력이 구속 조건일 것                       | 기각 | 예산 대비 하루 410질의 여유                 |
| PulseAudio가 PCM을 점유했을 것              | 기각 | `controlC*`만 점유, `pcmC*`는 비어 있음 |
| espeak-ng가 오디오 장치를 잡았을 것         | 기각 | `fuser`에 없음. `-w`는 장치를 열지 않음 |

**측정 도구 자체가 측정값을 오염시킨 사례가 세 건 있었다.**

1. 이전 세션의 `jetson_clocks`가 재부팅 전까지 유지되어, 5개 구성이 전부
   "클럭 고정" 상태에서 측정됐다. `clocks: as-is` 라벨이 사실은 "이미 고정됨"이었다.
2. `tegrastats --logfile`이 이어쓰기라 2회차부터 이전 실행의 전력 샘플이 섞였다.
   활성 전력이 7,490 → 7,388 → 7,005 → 6,702 mW로 단조 감소한 것이 그 흔적이다.
3. `tegrastats`가 root로 로그 파일을 만들어, 일반 사용자 권한의 truncate가 실패했다.

**값이 이상하면 워크로드를 의심하기 전에 하네스를 의심해야 한다.**
세 건 모두 지연·정확도는 무사했고 전력 값만 오염됐다 — 지연은 실행마다 독립적으로
파싱했기 때문이다. 측정 경로를 분리해 둔 것이 피해를 국소화했다.

### 5.8 측정 없이 판단했다면

| 직관                                | 실측                                  |
| ----------------------------------- | ------------------------------------- |
| GPU가 있으니 GPU를 쓴다             | CPU가 지연 2.7배, 에너지 2.4배 우세   |
| 정확도가 부족하면 모델을 키운다     | small이 더 느리고 더 위험한 오류를 냄 |
| `jetson_clocks`를 항상 켠다       | CPU 경로에서 효과 0.3%                |
| 컨텍스트를 줄이면 안전하게 빨라진다 | 지나치면 환각 + 12.6초                |
| 중앙값으로 성능을 판정한다          | 최댓값 기준으로 순위가 역전           |

다섯 개 중 다섯 개가 반대였다.

| G1 | 키워드 게이트 통과        | 6/6               | 안전 관련이라 부분 통과를 허용하지 않는다          |
| G2 | **최악 지연** + TTS | ≤ 2,000 ms       | 데모 조건이 연속 20회이므로 중앙값이 아니라 최댓값 |
| G3 | STT 상주 메모리           | 0, 피크 ≤ 0.5 GB | LLM 상주 1.4 GB와 경합 금지                        |

**최적화 목표** — 게이트를 통과한 것들 사이의 순위.

| 우선 | 목표                                  |
| ---- | ------------------------------------- |
| 1    | 인식 텍스트 품질 (안전 계약 직결)     |
| 2    | 최악 지연                             |
| 3    | 질의당 에너지                         |
| 4    | 운영 복잡도 (클럭 정책·부팅 절차 등) |

**지연 측정 기준점은 `버튼 뗀 순간 → 첫 소리`다.** 사용자가 체감하는 구간이 그것이기 때문이다.
내부 단계 합이 아니라 이 구간이 예산의 대상이다.

### 6.2 정확도를 WER로 재지 않는 이유

본 시스템은 받아쓴 문장을 사용자에게 보여 주지 않는다. **14개 라벨로 분류하는 데만 쓴다.**

```
said : 이 물 마셔도 돼
heard: 입을 마셔도 돼        "물" 소실, 그러나 "마셔"가 남아 water 라벨로 정상 라우팅
```

WER은 이 오류에 벌점을 매기지만 시스템 동작에는 영향이 없다.
반대로 WER이 낮아도 **라우팅 키워드 하나가 바뀌면 치명적**이다.

다만 현재 지표는 불완전하다(§6.4).

### 6.3 후보 구성 비교

전체 표는 [`decision_matrix.csv`](decision_matrix.csv)에 있다. 상위 두 개만 옮긴다.

|                     | **후보 A** `base_cpu_vad`     | **후보 B** `base_cpu_ac450nf` |
| ------------------- | ------------------------------------- | ------------------------------------- |
| 옵션                | `-ng -ac 450 -bo 1 -bs 1 -nf --vad` | `-ng -ac 450 -bo 1 -bs 1 -nf`       |
| G1 게이트           | 6/6 ✅                                | 6/6 ✅                                |
| G2 최악 지연 (+TTS) | **1,555 ms** ✅                 | 3,423 ms ❌                           |
| G3 메모리           | 147 MB ✅                             | 147 MB ✅                             |
| 중앙 지연           | 1,385 ms                              | **1,244 ms**                    |
| 질의당 에너지       | **1.22 mWh**                    | 1.48 mWh                              |
| 인식 오류           | `#2` 해치기, **`#4` 입을**  | `#2` 해치기                         |

**두 후보를 병기한다.** 현재 데이터만으로는 A가 유일하게 G2를 통과하지만,
B의 G2 미달 원인이 **5초 고정 녹음이라는 측정 하네스의 산물일 가능성**이 있다(E12).
제품은 푸시투토크라 무음이 생기지 않는다.

- E12에서 3초 녹음으로 B의 최댓값이 1,500 ms 근처로 내려오면 → **B 채택** (정확도 우위)
- 내려오지 않으면 → **A 채택**, `#4`의 키워드 소실은 다중 매칭 규칙으로 보완(§6.4)

### 6.4 지표 보강 — 현재 지표의 한계

키워드 게이트 통과율은 **"정답 라벨의 키워드가 살아남았는가"**만 본다. 세 가지를 못 본다.

| 못 보는 것                                  | 실제 사례                                                    |
| ------------------------------------------- | ------------------------------------------------------------ |
| 오인식이**다른 라벨의 키워드를 생성** | small의`이 물` → `이불` (침구 → `sleep_safety` 연상) |
| **두 라벨의 키워드가 동시** 매칭      | "불 피워도 되나 이 물 마셔도 돼" — 미설계                   |
| **`refuse` 누락**                   | 표본이 6발화 중 1개뿐이라 검증 불가                          |

추가할 지표:

| 지표                        | 정의                                | 기준                                  |
| --------------------------- | ----------------------------------- | ------------------------------------- |
| 게이트 재현율               | 정답 라벨 키워드 생존율             | 현재 6/6                              |
| **게이트 정밀도**     | 오인식이 만든 거짓 키워드 비율      | 0 목표                                |
| **`refuse` 누락률** | 식용 질문에서`refuse`를 놓친 비율 | **0. 다른 축과 맞바꿀 수 없음** |

`refuse` 누락은 안전 계약 6번 위반이다. 식용 표현 표본을 5~6개로 늘려 별도 세트로 측정한다.

**다중 매칭 처리 규칙 제안** (`config/keyword_rules.yaml` 미작성):

```
① refuse 키워드가 있으면    -> 무조건 refuse (다른 매칭 무시, 안전 편향)
② 정확히 한 라벨만 매칭     -> 그 라벨. 경로 B (2.0 s)
③ 두 개 이상 매칭          -> LLM 분류로 강등. 경로 A (3.5 s)
④ 하나도 매칭 안 됨        -> LLM 분류
```

즉 **모호하면 키워드가 결정하지 않는다.** 키워드는 확실할 때만 쓰는 지름길이다.

### 6.5 보드를 교체하지 않는 이유

"GPU가 졌으니 GPU 없는 SBC(라즈베리파이 5 등)로 바꾸면 되지 않는가"에 대한 답이다.

**① GPU가 진 조건을 한정해야 한다.**
whisper base는 74M 파라미터다. 이 규모에서는 커널 실행 오버헤드와 낮은 점유율이
연산량을 압도한다(§5.3). GPU가 무능한 것이 아니라 **일이 너무 작아 시동 비용을 못 뽑은 것**이다.

**② LLM은 20배 크다.**
Qwen2.5 1.5B Q4_K_M의 `prefill 413 tok/s`는 `00_frozen_decisions.md` §2에 기록된 GPU 경로 실측값이다.
CPU에서는 나올 수 없는 수치다.

**③ 따라서 교체는 STT를 개선하려고 LLM의 실행 타깃을 없애는 거래다.**

|                      | Jetson Xavier NX                            | RPi 5 8GB                                        |
| -------------------- | ------------------------------------------- | ------------------------------------------------ |
| STT (74M)            | CPU 1,385 ms`[실측]`                      | Cortex-A76이 Carmel보다 강해 개선 가능`[추정]` |
| **LLM (1.5B)** | **GPU, prefill 413 tok/s** `[실측]` | **GPU 가속 없음** `[추정]`               |
| 경로 A 3.5초         | 여유 있음                                   | **붕괴 위험** `[추정]`                   |

**④ 일정과 동결 제약.**
`00_frozen_decisions.md` §1에서 하드웨어는 동결이고 내부 동결일은 2026-09-01이다.
보드 교체는 부팅 매체·전원 게이팅·STM32 연동·외함 치수까지 전부 재작업이다.

**⑤ 결론은 그 반대다.**
"작업 크기에 따라 최적 실행 타깃이 다르다"가 본 실험의 결론이라면,
**한 보드에 CPU와 GPU가 같이 있는 편이 유리하다.** 실제로 설계가 더 깔끔해진다.

```
STT   -> CPU      GPU 미사용
LLM   -> GPU      CPU 경합 없음
TTS   -> CPU
```

기존 제약인 `STT·LLM·TTS 순차 실행`에서 STT와 LLM이 서로 다른 연산 유닛을 쓰게 되어
자원 경합이 줄어든다. 메모리 대역폭은 여전히 공유하므로 순차 실행 원칙 자체는 유지한다.

## 7. 결론 및 한계

### 7.1 결론

1. **이 워크로드에서 GPU는 지연과 에너지 양쪽에서 순손실이다.** CUDA 컨텍스트 초기화가
   질의당 1.6초의 고정비를 만들고, 74M 파라미터에서는 커널 오버헤드가 연산량을 압도한다.
2. **판정 지표는 중앙값이 아니라 최댓값이어야 한다.** 데모 조건이 연속 20회이기 때문이며,
   실제로 중앙값 1위 구성의 최댓값은 12.6초였다.
3. **모델을 키우는 것이 정확도의 답이 아니었다.** 키워드 게이트 통과율은 동일했고,
   큰 모델이 더 위험한 오류를 냈다.

### 7.2 한계

- **단일 기기·단일 워크로드**의 정적 선택이다. 다른 보드나 다른 모델 크기로 일반화되지 않는다.
- **정적 선택이므로 런타임 적응이 없다.** 배터리 잔량·온도·부하에 따라 타깃을 바꾸는
  동적 정책은 다루지 않았다.
- **발화 표본이 6개**다. 특히 `refuse` 표본이 1개뿐이라 안전 계약 검증에는 부족하다.
- **정확도 지표가 불완전하다.** 거짓 양성과 `refuse` 누락을 아직 측정하지 못한다.
- **espeak-ng 이후의 TTS를 측정하지 못했다.** 종단 지연은 espeak-ng 기준값이다.
- **20회 연속 지속 부하에서의 열 거동을 확인하지 않았다.**
- E0의 EBUSY는 **근본 원인을 확정하지 못한 채 폴백으로 우회**했다.
