| **STT 도메인 프롬프트** | **채택 (거짓 양성 0 조건)** | base에서 `목적지` 복구에 +87 ms `[실측]`. 누출 상한은 21문장 거짓 양성 |
| **STT `-ac 450`** | **필수** | 30초 멜 윈도 패딩이 지연의 81%. 16,933 → 1,494 ms `[실측]` |
| STT beam search | **제외** | 지연 +33%, 출력 변화 없음 `[실측]` |
| STT GPU 실행 | **금지** | `-ng` 미지정 시 cudaMalloc 91 MiB 실패 → SIGSEGV `[실측]` |

**메모리 예산 (6.8GB 기준):**
OS+데스크톱 ~1.0 / Chromium kiosk ~1.2 / Python 백엔드 ~0.3 / **LLM 상주 ~1.4** /
**STT 온디맨드 ~0.5** / **TTS 온디맨드 0.5~1.5** → 동시 피크 4.9~5.9.
게이트 **`MemAvailable ≥ 1GB`** 유지. **STT와 TTS를 동시에 올리지 않습니다.**

**전력 예산 (14일 기준):**
S1 감시 0.35 W × 14h + S2 항법 0.55 W × 10h + S3 화면 13 W × 23분 + **S4 응답 18 W × 100초**
= 약 230 Wh → 손실·마진 포함 **330 Wh**. 상시 구동은 4,200 Wh로 물리적으로 불가능.

**S4 예산은 하루 500 mWh**입니다. STT 단독 실측은 질의당 **1.22~2.31 mWh** `[실측]`
(Xavier NX, whisper base, CPU 백엔드. 근거는 `measurements.csv`).
이 축에서는 **전력이 아니라 지연이 구속 조건**입니다.

## §3 안전 계약 — 절대 규칙

원본은 `OGTECH-org/docs/AI_AGENT_GUIDE.md`이며, 충돌하면 그쪽이 우선합니다.

1. **경로·방위·거리는 절대 LLM이 생성하지 않습니다.** 지도 엔진(코드)이 GPS와 타일 데이터로 계산하고 LLM은 읽어 주기만 합니다. **출력 스키마에 숫자 필드를 두지 않는 것**이 기계적 강제 수단입니다.
2. **생명 관련 응답은 LLM을 거치지 않습니다.** `lost / daylight / warmth / sleep_safety / injury`는 키워드 게이트 → 검수된 고정 카드 → TTS 직행입니다.
3. **이 장치는 구조 요청 수단이 아닙니다.** 조난 예방과 자력 탈출만 담당하며, 이 한계를 부팅 시 1회 건너뛸 수 없게 표시합니다.
4. **GPS 미수신을 위치 추정으로 덮지 않습니다.** 마지막 확정 좌표 + 경과 시간만 표시하고, 측위 정확도(±m·위성 수)를 항상 같이 표시합니다.
5. **사용자에게 보이는 절차 문구는 검수된 고정 카드뿐입니다.**
6. **금지 생성:** 진단, 약물명·용량·복용법, 침습 처치, **야생 동식물 식용 판정**, 구조 필요 여부 판단, 계속 진행/철수 결정, 방위·거리·경로. 식용 관련 질문은 **모델 도달 전 키워드 게이트가 차단**합니다.
7. **센서 확인 없이 확정 상태로 표시하지 않습니다.** 기상은 항상 `추정` 배지를 답니다.
8. **모의 값이 하나라도 섞이면 `DEMO`를 화면에서 숨기지 않습니다.**
9. **오프라인 동작을 항상 보존합니다.** 지도·일출몰·기상 추정·항법은 전부 로컬 계산이어야 합니다.
10. 비밀값·Wi-Fi 자격 증명·개인정보·**실제 GPS 트랙**·비공개 내보내기를 커밋하지 않습니다.

## §4 LLM 계약

LLM은 판단 주체가 아니라 **정해진 계약 안에서 텍스트를 다루는 부품**입니다. 설계상의 역할은 3개였습니다.

| # | 작업 | 입력 | 출력 | 출력 한도 |
|---|---|---|---|---|
| 1 | 시나리오 분류 | 사용자 발화 | 14개 라벨 중 하나 | **라벨 1개** |
| 2 | 질의 대상 추출 | 사용자 발화 | `target` × `ask` | 값이 아니라 "무엇을 묻는지"만 |
| 3 | 카드 맞춤 문장 | 선택된 카드 + 장치 상태 | 2~4줄 | ~96 토큰 |

> `[정합화 주석]` (2026-08-21) — **현재 코드에 구현된 것은 1번뿐입니다.**
> 2·3번은 설계 목표로 남아 있고 구현되지 않았습니다. 문장 생성은 LLM이 아니라
> `scripts/ogtech_core.py`의 `CardRenderer`가 검수 카드 문장과 장치 계산값 템플릿으로 만듭니다.
> 자세한 현황은 저장소 최상위 `README.md`의 "LLM이 실제로 하는 일" 표를 보세요.

허용 `scenario_id` (14개):
`lost, route, daylight, weather, shelter, warmth, water, food, sleep_safety, injury, wildlife, gear, refuse, unknown`

**응답 경로 2개 — 라벨이 경로를 결정합니다.**

```
경로 B (LLM 우회, 목표 <= 2.0 s)
  lost / daylight / warmth / sleep_safety / injury / refuse
  -> 키워드 게이트 -> 고정 카드 -> TTS 직행

경로 A (LLM 다듬기, 목표 <= 3.5 s)
  route / weather / water / food / shelter / wildlife / gear
  -> 분류 -> 고정 카드 -> LLM 2~4줄 -> 문장 단위 스트리밍 TTS
```

### §4 실패 처리

- 구조화 출력은 **JSON Schema 제약**으로 강제합니다 (llama.cpp가 GBNF로 자동 변환).
- **재시도는 넣지 않습니다.** 문법 실패가 구조적으로 0이 되므로 재요청 단계가 불필요합니다.
- enum, 금지어, 출처 ID 존재 여부는 **코드에서** 검증합니다.
- 검증 실패 또는 **2초 초과** → 재시도 없이 즉시 고정 화면으로 전환합니다.
- `confidence` 필드는 **스키마에 없습니다.**
- **좌표·방위·거리 숫자 필드는 스키마에 존재하지 않습니다.** 자리가 없으면 환각도 없습니다.

### §4 생성 설정

`temperature = 0`. 취향이 아니라 재현성 문제입니다 — 리허설 20회 연속 동일 출력을 보장해야 합니다.

## §5 하네스 규칙

### §5 프롬프트 조립 순서 — 불변 → 준가변 → 가변

```
[SYSTEM + 출력 규칙]   ← 완전 고정, KV 캐시에 남음
[SURVIVAL_CARD]        ← 선택된 카드 1장, 60~120 tok. 세션 내 준고정
[DEVICE_STATE]         ← 요청마다 변함. 40~60 tok 상한
[USER]                 ← 마지막
```

`DEVICE_STATE`를 앞에 두면 매 요청 KV 캐시가 통째로 무효화됩니다.

### §5 DEVICE_STATE 상한 — 60 토큰

```
포함: gps(fix/lat/lon/acc_m/age_s) · time(now/sunset/civil_end/remaining_min)
      env(temp_c/humidity/press_hpa/press_trend) · power(pct/days_left)
      route(on_trail/offset_m/next_wp_m)
제외: 전체 GPS 트랙 · 위치 로그 목록 · 지도 타일 · 카드 원문 발췌 · 대화 이력 전체
```

### §5 지연 병목은 모델이 아니라 프롬프트 길이입니다

Xavier 실측 **prefill 413 tok/s**입니다. 프롬프트 토큰이 곧 지연입니다.
**3,300토큰짜리 프롬프트는 prefill만 8초입니다.** 60토큰 상한을 지키세요.

### §5 llama-server 실행 옵션

```
-fa
--cache-type-k q8_0
--cache-type-v q8_0
--cache-reuse 256
--mlock
-b 512 -ub 512
--threads 4~6
--parallel 1
```

- LLM 모델은 **상주**시킵니다. **STT·TTS는 온디맨드 로드/언로드**이며 동시에 올리지 않습니다.
- swap을 늘려 통과시키지 않습니다.

### §5 STT 실행 구성

whisper.cpp + **CPU 백엔드**입니다. 근거·원시 데이터는 `01_main.md`, `measurements.csv`,
`03_appendix_raw_log.md`에 있습니다.

```
-ng -ac 450 -bo 1 -bs 1 -nf -t 6 -l ko -nt
--prompt "<도메인 프롬프트>"        # 아래 '초기 프롬프트 계약' 참조
```

- **`-ng`는 선택이 아니라 필수입니다.** 빼면 91 MiB cudaMalloc에 실패해 **SIGSEGV로 죽습니다** `[실측]`.
- **스레드는 병목이 아닙니다.** 4→6에서 9% `[실측]`. `nproc 6`이 이미 최대입니다.
- **beam search 기각.** 지연 +33%에 출력이 한 글자도 안 바뀝니다 `[실측]`.
- **`jetson_clocks`는 CPU 경로에서 효과 0.3%** `[실측]`.
- **FlashAttention은 켜 두는 쪽이 유리** — 끄면 encode 34% 악화 `[실측]`.
- `-ac`를 300까지 줄이면 환각과 12.6초 폭주가 발생합니다 `[실측]`. **450이 하한선입니다.**
- **동일 구성·동일 입력의 실행 간 편차가 최대 1.7배입니다** `[실측]`. 단일 실행으로 구성을 판정하지 마세요.

> `[정합화 주석]` (2026-08-21) — **VAD는 원문 이후에 결정되었습니다.**
> 원문 §10 미결 #8이 "VAD 사용 여부"를 열어 둔 채였고, 그 뒤 P5 벤치에서 결론이 났습니다.
> `measurements.csv`의 `base_cpu_vad` 행이 **"최종 선정"**, `decision_matrix.csv`의 같은 구성이
> **"선정 — 최댓값 기준으로 예산을 통과한 유일한 구성"**입니다.
> 따라서 **현재 동결 플래그는 위 목록 + `--vad -vm <ggml-silero-v5.1.2.bin>`** 입니다.
> 재현 명령은 `02_appendix_reproduction.md`에 있습니다.
> 남은 이견: `01_main.md` §6.3이 후보 B(`-ac 450 -nf`, VAD 없음)를 병기하며 **E12(3초 녹음 재측정)** 결과에

### §5 초기 프롬프트 계약

**도메인 프롬프트(컨텍스트 바이어싱)를 채택합니다.** base에서 `목적지`를 살리는 데 +87 ms `[실측]`.

**그러나 whisper의 초기 프롬프트는 어휘 사전이 아니라 "다음에 올 텍스트"의 사전확률입니다.**
오디오가 모호하면 프롬프트를 그대로 이어 씁니다. 네 번의 시행에서 전부 누출됐습니다 `[실측]`.
**키워드 게이트는 텍스트만 보므로 환각과 실제 발화를 구분할 수 없습니다.**

작성 규칙:

1. **목록 금지, 문장으로.** 쉼표 명사 목록은 출력 형식까지 복사시킵니다 `[실측]`
2. **실사용·평가 발화와 겹치지 않게.** 겹치면 인식인지 복사인지 구분 불가 `[실측]`
3. **평서문으로.** 실사용이 의문문이므로 프롬프트가 의문문이면 누출이 더 그럴듯해집니다 `[추정]`
4. **길이는 거짓 양성이 허용하는 만큼.**

**채택 조건은 하나입니다 — `04_record_set.sh`의 21문장에서 거짓 양성 0.**
특히 `#17 먹을 거 다 떨어졌어`(→`버섯`/`열매` 금지)와 `#21 이불 챙겨왔어야 했는데`(→`물`/`마셔` 금지)를 봅니다.

### §5 측정 기준

- **지연 기준점은 `버튼 뗀 순간 → 첫 소리`**입니다.
- **판정은 중앙값이 아니라 최댓값으로 봅니다.** 데모 조건이 연속 20회이므로 한 번의 이상치가 곧 실패입니다.
  실제로 중앙값 1위 구성의 최댓값이 12.6초였습니다 `[실측]`.
- **정확도는 WER이 아니라 키워드 게이트 지표로 봅니다.**
- **재현율과 정밀도를 같이 봅니다.** `05_bench.sh`가 금지 키워드 등장을 `false_pos`로 셉니다.

**판정 순서는 정확도가 아니라 안전이 먼저입니다.**

```
① 안전 문장을 놓치지 않는가   #13 버너(CO) · #15/#16 refuse
② 거짓 양성 0인가             #17 · #21
③ 최댓값이 예산 안인가
④ 중앙값
```

### §5 실행 타깃 원칙

**작업 크기에 따라 최적 실행 타깃이 다릅니다.**
74M 파라미터(whisper base)에서는 커널 실행 오버헤드가 연산량을 압도해 CPU가 유리하고,
1.5B(Qwen2.5)에서는 GPU가 유리합니다(`prefill 413 tok/s [실측]`).

```
STT  -> CPU      GPU 미사용
LLM  -> GPU      CPU 경합 없음
TTS  -> CPU
```

**메모리 대역폭은 공유하므로 순차 실행 원칙은 그대로 유지**합니다.

### §5 분류 최적화 순서

```
1차: 키워드 규칙 (0 ms) — "먹/식용/버섯" -> refuse 를 최우선 매칭
2차: 1차 미스 시 LLM 라벨 1개 생성 (~0.6 s)
3차: unknown -> 고정 안내 카드 + FTS5 검색 화면
```

14-way 분류에 20~40토큰 JSON을 생성하는 건 낭비입니다. 라벨 1개만 생성합니다.

다중 매칭 우선순위(원문에서는 미결 #9의 제안, 현재는 `config/keyword_rules.yaml`로 구현됨):

```
① refuse 키워드가 있으면  -> 무조건 refuse (다른 매칭 무시, 안전 편향)
② 정확히 한 라벨만 매칭   -> 그 라벨. 경로 B
③ 두 개 이상 매칭        -> LLM 분류로 강등. 경로 A
④ 하나도 매칭 안 됨      -> LLM 분류
```

**모호하면 키워드가 결정하지 않습니다.**
